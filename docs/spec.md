# Спецификация

## Что измеряем

Реестр сессий Claude Code отдаёт по каждой сессии два блока. Оба лежат внутри
`external_metadata`, а сама запись обёрнута в `ccr`; список ещё и страничный —
`has_more` говорит, что записи кончились не все:

```json
{"ccr": {"data": [{"id": "session_…",
                   "external_metadata": {"usage": {…},
                                         "rate_limit_info": {…}}}],
         "has_more": true}}
```

Форма снята замером живого ответа 2026-09-02. Прежняя редакция этого раздела
показывала оба блока на верхнем уровне записи — читатель, написанный по ней, не
нашёл бы ничего и сказал бы «замерять нечего»: отказ верный по форме и ложный
по сути.

**Состояние лимита** — светофор:

```json
"rate_limit_info": {
  "rateLimitType": "seven_day",
  "resetsAt": 1787731200,
  "status": "allowed_warning",
  "isUsingOverage": false
}
```

**Фактический расход**:

```json
"usage": {
  "cache_read_tokens": 89595066,
  "cache_write_tokens": 1104683,
  "input_tokens": 61369,
  "output_tokens": 182703,
  "cost_usd": 106.66
}
```

Ни процента остатка, ни абсолютного лимита в этих данных нет. Есть три ступени
(`allowed` → `allowed_warning` → `rejected`), время сброса и расход.

## Как из этого получается остаток

1. **Замер.** Пройти по всем сессиям аккаунта, снять `usage` и
   `rate_limit_info`, записать строку JSONL с меткой времени.
2. **Расход за окно.** Просуммировать по сессиям, попадающим в пятичасовое и
   семидневное окно.
3. **Калибровка.** Запомнить суммарный расход в момент перехода
   `allowed → warning` и `warning → rejected`. Эти точки и есть шкала.
4. **Вывод.** Пока калибровочных точек нет — сообщать расход и честно писать,
   что остаток неизвестен. Когда появились — считать долю.

Калибровка требует **событий, а не времени**: без переключений светофора шкалы
не будет, сколько бы замеров ни накопилось.

## Формат хранения

JSONL, одна строка — один замер, только дописывание. В замер идут **все пять**
чисел расхода, которые отдаёт реестр, а не выборка из них.

```
{"ts":"2026-08-21T09:10:03Z","session":"…","source":"registry","complete":true,"sessions":12,"type":"seven_day","status":"allowed_warning","resets_at":1787731200,"cache_read":89595066,"cache_write":1104683,"input":61369,"output":182703,"cost_usd":106.66}
```

## Полнота выгрузки: поля `complete` и `sessions`

Реестр **страничный**: `has_more` говорит, что записи кончились не все, и сумма
по такой выгрузке занижена на неизвестную долю. Шкала строится по СУММЕ в
момент переключения светофора, поэтому калибровочная точка на неполной сумме
неверна — а в файле она выглядит точно так же, как полная.

Поэтому реестровая строка несёт полноту той выгрузки, из которой взята:

| поле | что значит |
|---|---|
| `complete` | видели ли мы все записи реестра в этот замер |
| `sessions` | сколько записей было в выгрузке — **включая окна без расхода** |

Строк с расходом в файле столько, сколько записалось; разница с `sessions` и
есть число мостовых окон, у которых блока `usage` нет вовсе.

Аргументы сборки строки **обязательны и без умолчания**: умолчание «выгрузка
полная» соврало бы молча, а в append-only хранилище такая ложь не чинится.

**У транскриптных строк этих полей нет.** Их полнота — другая величина: файлы
читаются целиком, но видны только окна своей машины. Одно поле на две разные
величины было бы хуже отсутствия.

## Откуда взято число: поле `source`

Источников два, и они дают **разные числа по одному и тому же окну**. Первый
замер (2026-09-02) показывал расхождение в 3,6–5,5 раза и был объяснён тем, что
источники меряют разные величины. Объяснение оказалось **неверным**, и вот чем
оно заменено.

**Главная часть расхождения была нашей собственной ошибкой чтения.** Транскрипт
пишет по строке на каждый блок содержимого ответа — текст, рассуждение, каждый
вызов инструмента, — и `usage` в этих строках стоит один и тот же: полный расход
ответа, а не доля. Сложение строк подряд множило расход на число блоков.

Замер 2026-09-03, второе окно, 267 строк с расходом на **132 ответа**:

| число | по строкам | по ответам | реестр |
|---|---:|---:|---:|
| `output` | 257 434 | 115 291 | 82 510 |
| `cache_read` | 52 241 255 | 26 698 822 | 17 028 502 |

Отношение к реестру после дедупликации упало с 3,0× до 1,35–1,5×.

**Остаток объясняется тем, что `usage` реестра — отстающий снимок.** Два запроса
к реестру с интервалом 80 секунд: `updated_at` сдвинулся, `usage` не изменился
ни на один токен. То есть агрегат обновляется реже, чем сама запись, и на живом
окне он заведомо старее транскрипта.

**Одно расхождение остаётся необъяснённым:** `input` у реестра больше, чем у
транскрипта (702 против 266 во втором замере, 13 135 против 2 646 в первом) —
единственное число, растущее в обратную сторону. Правдоподобно, что реестр
считает и служебные вызовы модели, которых в транскрипте нет вовсе: заголовок
сессии, краткое описание задачи. Это гипотеза, а не измеренный факт.

Разбор: [#52](https://github.com/ArtVsMark/Claude-Code_Usage-Token/issues/52).

Складывать источники всё равно **нельзя**, и заполнять пробел одного из
другого — тоже: одно окно попало бы в сумму дважды, а отстающий снимок
смешался бы со свежим помессажным счётом. Поэтому каждая строка несёт
`source`: `registry` либо `transcript`.

Причина запрета, однако, изменилась — и это разница, а не оттенок. Раньше
считалось, что источники несопоставимы **по природе**; теперь известно, что они
меряют одно и то же с разной свежестью и разной полнотой. Значит вопрос
«какая величина связана со светофором» перестал быть выбором между двумя
несравнимыми шкалами.

У транскриптной строки **нет `cost_usd`** — его отдаёт только реестр. Считать
стоимость по ценам модели значило бы выдать оценку за факт, писать нулём —
соврать молча. У неё же нет состояния светофора (`type`, `status`,
`resets_at`): оно приходит с записью реестра. Такая строка годится для суммы
расхода, но не для калибровочной точки.

Поле заведено **до первой записанной строки** и по замеру, а не из
аккуратности: состав полей задним числом не меняется.

Состав полей менять нельзя задним числом: хранилище append-only, а замер —
снимок на момент запроса. Не записанное сейчас не восстановится, и в накопленных
данных навсегда останется граница, до которой расход учтён не полностью.
Разбор и доводы — [#18](https://github.com/ArtVsMark/Claude-Code_Usage-Token/issues/18).

Хранилище — **приватный репозиторий**
[`Claude-Code_Usage-Data`](https://github.com/ArtVsMark/Claude-Code_Usage-Data),
файл `samples/usage.jsonl` в `main`. Отдельная ветка не нужна: репозиторий и
так только под данные.

На файл ставится `merge=union` в `.gitattributes` — append-only строки
сливаются без конфликтов, даже когда пишут несколько окон разом. Отсюда два
следствия, обязательных для читателя:

- **строки не редактируются и не удаляются** — исправление это новая строка,
  иначе слияние перестаёт быть предсказуемым;
- **порядок строк не гарантирован** — слияние объединяет, но не сортирует;
  упорядочивать по `ts` обязан читатель.

## Почему git, а не база и не сервер

Замер может сделать **только окно**: данные живут в реестре сессий (MCP), а не
в GitHub — workflow в Actions туда не достучится.

При этом облачное окно **эфемерно**: файловая система исчезает вместе с
контейнером, локальная база бессмысленна.

Значит хранилище обязано быть внешним. Git подходит лучше сервера: он
распределённый, версионированный и доступен из любого окна. Сервер добавил бы
точку отказа, а при агрегации чужих данных — ещё и согласие, политику
приватности и ответственность за хранение.

## Что инструмент делает

- `sample` — снять замер и дописать в хранилище;
- `report` — расход за окно, состояние светофора, время сброса, остаток по
  калиброванной шкале (или честное «неизвестен»);
- `calibrate` — пересчитать шкалу по накопленным переходам.

## Частота

По умолчанию **15 минут**, флаг `--min-interval` (`0` снимает порог).

Число не круглое из воздуха: при такой частоте пятичасовое окно набирает два
десятка точек, а семидневное — под семьсот. Чаще смысла нет — светофор
переключается за часы, а лишние строки дают шум и пачки коммитов.

Порог считается **по источнику**: реестр и транскрипт меряют разные величины,
и частота у них своя.

## Путь к хранилищу

Переменная `CLAUDE_CODE_USAGE_STORE` либо флаг `--store`; флаг важнее. Файла
конфигурации намеренно нет — третий источник истины пришлось бы держать в
согласии с двумя первыми, а надобности в нём пока не возникло.

## Как окно снимает замер

Реестр живёт в MCP, а MCP есть у **окна**, не у процесса Python. Поэтому окно
спрашивает реестр само и кладёт ответ в файл:

```
claude-code-usage-meter sample --registry ответ.json
```

Транскрипты лежат на диске, и их инструмент читает сам: `--transcripts`.

## Границы

- **Не** хранит содержимое сессий, токены и ключи — только расход и состояние.
- **Не** зависит от соседних проектов: связь с ними только документационная.
- **Не** обещает точности до процента, пока не набрана шкала, и говорит об этом
  прямо.

## Погрешность

Часть вывода, а не отладочная информация: сколько замеров легло в оценку, когда
был последний, сколько калибровочных точек.

Замер — снимок на момент запроса. Расход завершившейся сессии может дописаться
позже, поэтому окно нельзя считать закрытым сразу после последнего замера.
